# Как проводится эксперимент и откуда берутся данные

Короткое практическое руководство к протоколу [`PILOT.md`](PILOT.md): что делается до, во время и после пилота,
где лежат данные и какими командами их достать. Пороги и гипотезы — в `PILOT.md`, здесь только порядок действий.

## 1. Что именно проверяется

Платформа сама записывает всё, что делает ученик, поэтому эксперимент — это не отдельная программа, а обычная
учёба первокурсников на курсе `python-intro` (8 миссий) и, для быстрых, `python-continued`. Дополнительно включено:

| Что | Как устроено | Гипотеза |
|---|---|---|
| Баннер помощи после 3 неудач подряд | половина учеников (случайно, по хешу id; `HELP_OFFER_SHARE=50`) видит баннер и бесплатную подсказку, вторая половина — контроль | H2 |
| Список раннего предупреждения | каждую ночь снимок списка «срочно / внимание / норма» (`snapshot_early_warning`) | H3 |
| Неудачи подряд | считаются по попыткам шагов | H1 |
| Здоровье измерений | сбои песочницы, ученики без следа | H4 |
| Прогноз результативности | составной балл (решённые шаги, звёзды, ответы «объясни»), модель обучается после пилота | глава о прогнозе |

Единица анализа — **ученик** (интервалы по ученику, не по паре «ученик × шаг»). В расчёт идут только участники
исследования: дали согласие (`research_consent`) и зарегистрировались не раньше `PILOT_STARTED_AT`.

## 2. Откуда берутся данные

Все данные — в базе Postgres на Railway (сервис бэкенда `diplom-work-main-production.up.railway.app`).
Отдельного сбора нет: каждая запись появляется, когда ученик работает на сайте.

| Таблица (модель) | Что в ней | Для чего |
|---|---|---|
| `game_learningevent` (`LearningEvent`) | события: открыл шаг, ответил, взял подсказку, позвал Мудреца, спасательная подсказка, ушёл со вкладки | активность, «признаки жизни», H1–H3, паттерны поведения |
| `game_coderun` (`CodeRun`) | каждый запуск кода: результат, ошибка, время, сколько набрано и вставлено | паттерны, сбои песочницы (H4) |
| `game_taskprogress` (`TaskProgress`) | попытки и итог по каждому шагу | неудачи подряд (H1), H2, балл |
| `game_progress` (`Progress`) | миссии: завершение, звёзды, XP | завершение курса, балл |
| `game_earlywarningsnapshot` (`EarlyWarningSnapshot`) | ежедневный снимок списка предупреждений | H3 (честная проверка прогноза) |
| `game_usabilityresponse` (`UsabilityResponse`) | анкета SUS преподавателя | удобство кабинета |
| `users_profile` (`Profile`) | согласие и время согласия, уровень, предметы | кто входит в выборку |

Данные Таверны (`social_*`: друзья, обмены, гильдии, дуэли) **в исследовательские таблицы не пишутся** и в
выгрузки не попадают. Если протокол не включает Таверну, на время пилота поставьте `SOCIAL_ENABLED=0`:
обмен меняет запас подсказок (H2); дуэли берут вопросы только из миссий, которые оба игрока уже прошли.

Метод прогноза проверен отдельно на открытом наборе **OULAD** (Open University, 32 593 студента, лицензия
CC BY 4.0). Он скачивается с сайта Open University (analyse.kmi.open.ac.uk, раздел Open University Learning
Analytics dataset) и кладётся в `ml/data/oulad/` (в git не входит). Повторить расчёт: `cd ml`,
`python -m risk.train --oulad data/oulad --out out/oulad` — отчёт в `out/oulad/report.md` (итог на 2026-10-13:
ROC AUC 0,65–0,67, модель не лучше одного счётчика активных дней).

## 3. До старта (один раз)

1. На Railway → сервис бэкенда → Variables задать:
   - `PILOT_STARTED_AT` и `PILOT_ENDED_AT` с часовым поясом, например `2026-11-16T00:00:00+05:00` и
     `2026-12-28T00:00:00+05:00` (6 недель, конец — до сессии);
   - `HELP_OFFER_SHARE=50`, `ANALYTICS_EXPORT_SALT` (длинная случайная строка, не менять до конца);
   - свой `TEACHER_INVITE_CODE` (публичный `PILOT-2026` на проде не принимается);
   - `SOCIAL_ENABLED=0`, если Таверна не входит в протокол; `RISK_MODEL_PATH` оставить пустым.
2. Railway → New → Cron: `python manage.py snapshot_early_warning` по расписанию `0 19 * * *` (полночь UTC+5)
   и `python manage.py prune_learning_data` по `0 3 * * *`.
3. Репетиция на 2–3 знакомых за неделю до старта, затем `python manage.py pilot_check` — не должно быть FAIL.
4. Студентам — информационный лист и согласие (галочка при регистрации или в профиле). Без согласия ученик
   учится как обычно, но в расчёты не входит.

**Перед первым занятием (по итогам проверки 9 ноября):**
- регистрацию на уроке лучше делать **без e-mail** (поле необязательное): если на Railway включён Resend, ученик с
  почтой не войдёт, пока не подтвердит письмо, а школьная почта часто их не пропускает;
- код учеников проверяет публичный `ce.judge0.com`, одновременно не больше 4 запусков с сервера: при классе из
  30 человек запуск может ждать 5–15 секунд. Для пилота надёжнее свой Judge0 или ключ RapidAPI
  (`RUNNER_JUDGE0_URL`, `RUNNER_JUDGE0_KEY`);
- в собственных курсах преподавателя у кодовых шагов должна быть скрытая проверка или эталонный вывод (Студия
  теперь не сохранит шаг без них), а курс должен быть опубликован — иначе код класса ученики не введут.

Команды `manage.py` на Railway запускаются в консоли сервиса (Railway → сервис → кнопка с терминалом) или
со своего компьютера: `railway login`, `railway link`, затем `railway run python manage.py <команда>` из папки
`backend`.

## 4. Во время пилота

- **Каждый день** (2 минуты): `python manage.py pilot_check` — есть ли снимок за вчера. Пропущенный день для
  H3 не восстановить.
- **Каждый контакт** преподавателя с учеником из «срочно» или «внимание» — строка `username,ГГГГ-ММ-ДД` в
  `contacts.csv` у себя на компьютере (нужно, чтобы отделить эффект помощи от качества прогноза).
- **Раз в неделю**: `python manage.py pilot_report > week-N.md` и сохранить файл у себя (в контейнере он
  пропадёт при деплое).
- В кабинете преподавателя (`/teacher`) — живая панель, список предупреждений, путь каждого ученика; на
  `/analytics` — показатели и выгрузка CSV (`learning_metrics.csv`) по своим ученикам.
- Код и настройки во время пилота не менять, кроме исправления ошибок; каждое исправление записывать с датой.

## 5. После пилота: как достать данные

Со своего компьютера против боевой базы (в Railway → Postgres → Connect взять публичный `DATABASE_URL`).
На компьютере обязательно задать те же переменные, что на Railway, иначе выгрузка возьмёт не ту когорту или
другие псевдонимы (о пустой соли команды теперь предупреждают):

```bash
# PowerShell: $env:VAR="..." ; bash: export VAR="..."
DATABASE_URL=<публичный адрес Postgres из Railway>
PILOT_STARTED_AT=2026-11-16T00:00:00+05:00
PILOT_ENDED_AT=2026-12-28T00:00:00+05:00
ANALYTICS_EXPORT_SALT=<то же значение, что на Railway>
DJANGO_SETTINGS_MODULE=core.settings.local
```

Затем:

```bash
cd backend
python manage.py pilot_report --contacts ../contacts.csv > ../final_report.md
python manage.py pilot_report --json > ../final_report.json
python manage.py export_learning_data --out ../analytics_export
python manage.py export_risk_features --include-performance --out ../risk_features.csv --performance-out ../performance.csv
```

- `export_learning_data` пишет в папку `users.csv`, `tasks.csv`, `runs.csv`, `events.csv`,
  `task_progress.csv`, `mission_progress.csv` — только участники исследования, вместо id — псевдонимы.
- `export_risk_features` — таблица «окно признаков → исход» для модели (окна обрезаны по `PILOT_ENDED_AT`,
  в каждой строке уровень правил из снимка накануне) и `performance.csv` — одна строка на ученика для
  прогноза балла.

Затем обучение и честное сравнение (на своём компьютере, в образе Railway нет scikit-learn):

```bash
cd ml
pip install -r requirements.txt
python -m risk.train --features ../risk_features.csv --performance ../performance.csv --out ../risk_model
```

В `risk_model/report.md`: модель против одного `active_days` и против правил платформы на тех же строках,
разницы ROC AUC с 95% интервалом бутстрепа по ученикам, прогноз балла против среднего. Модель подключается
(`RISK_MODEL_PATH`) только если нижняя граница интервала разницы с лучшей планкой выше 0 (правило записано до
пилота). При малой выборке в диссертацию идёт метод и числа с интервалами, без выводов о превосходстве.

## 6. Что сказать комиссии честно

- Одна когорта на 30–60 согласившихся даёт **оценку с интервалом**, а не доказательство: для H2 нужно
  ≥ 30 пар и ≥ 15 учеников в группе, для модели — около 60 ушедших учеников.
- H2 — рандомизированное сравнение; H1 и H3 — наблюдательные.
- Помощь преподавателя по списку смещает H3 к нулю (поэтому журнал контактов).
- Перенос модели с OULAD на платформу не предполагается: на OULAD проверен метод, рабочая модель обучается на
  данных пилота.
