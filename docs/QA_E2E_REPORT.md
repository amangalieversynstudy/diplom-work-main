# Отчёт о ручном E2E-тестировании информационной системы «RPG Academy»

**Версия отчёта:** 1.0  
**Дата проведения:** 22 мая 2026 г.  
**Тестовая среда:** Docker Compose (`docker-compose.yml`), Python 3.11, PostgreSQL 15, Redis 7, Next.js 13  
**Тестировщик:** инженер по обеспечению качества проекта  
**Объект тестирования:** монолитное веб-приложение RPG Academy (backend — Django REST Framework, frontend — Next.js, изолированная песочница исполнения кода на базе Docker-in-Docker)

---

## 1. Цель и область тестирования

Целью ручного сквозного (end-to-end) тестирования являлась верификация ключевого пользовательского сценария «студент-практикант», объединяющего модули аутентификации, игровой прогрессии, защищённого исполнения кода и интеллектуального ассистента на базе модели Gemini. Тестирование носит характер приёмочного и проводится перед демонстрацией системы аттестационной комиссии.

Тестируемый сценарий охватывает следующие функциональные модули:

- модуль регистрации и активации учётной записи (`POST /api/auth/register/`, `EmailVerificationToken`);
- модуль аутентификации по JWT (`POST /api/auth/jwt/create/`, refresh-rotation);
- модуль выбора игрового класса и стартовой инициализации профиля (`PATCH /api/profile/me/`);
- модуль прохождения миссии (`POST /api/missions/{id}/start/`, `POST /api/missions/{id}/complete/`);
- модуль безопасного исполнения пользовательского Python-кода в Docker-песочнице (`POST /api/runner/execute/`, WebSocket `/ws/runner/`);
- модуль AI-помощника на базе Gemini 1.5 Flash (`POST /api/ai-assist/`);
- модуль начисления игрового опыта (XP), повышения уровня и обновления ранга (`Profile.add_xp()`, `Profile.current_rank`).

Из области тестирования исключены подсистема платежей (удалена из проекта в рамках перехода к бесплатной модели распространения) и подсистема push-уведомлений (вынесена в backlog).

## 2. Методика тестирования

Тестирование проводилось по методике сквозных пользовательских историй (user journey) с ручным взаимодействием через интерфейс веб-приложения (Next.js, порт 3000) и параллельным контролем серверного состояния посредством инструментов наблюдения:
- журналы контейнеров (`docker compose logs backend`),
- интерфейс Django Admin (`/admin/`),
- интроспекция базы данных через `psql`,
- интерактивная оболочка Django (`manage.py shell`).

Каждый сценарный шаг сопровождался фиксацией трёх типов наблюдений: видимая для пользователя реакция интерфейса; запись в журнале серверных событий; изменение состояния модели в реляционной базе данных. Полнота сценария считается достигнутой только при положительном результате на всех трёх уровнях наблюдения.

## 3. Сценарий E2E-тестирования

### 3.1. Шаг 1. Регистрация нового пользователя

**Входные данные:** `username=e2e_user`, `email=e2e@test.com`, `password=StrongP@ss123`.

**Действия пользователя:** заполнение формы на странице `/register`, отправка через нажатие кнопки «Создать аккаунт».

**Ожидаемый результат:** создание объекта `User` в базе данных, генерация одноразового токена верификации `EmailVerificationToken`, отправка письма с активационной ссылкой, перенаправление на страницу с сообщением «Подтвердите почту».

**Фактический результат:**
- HTTP-запрос `POST /api/auth/register/` завершился со статусом `201 Created`, в теле ответа возвращён сериализованный пользователь;
- в журналах сервиса `backend` зафиксирована полнотекстовая копия письма (используется console-EmailBackend, директива `EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"` в `core/settings/base.py`), содержащая активационную ссылку вида `http://localhost:3000/verify-email?uid=OQ&token=d8zfy2-bddb12bb371bc95dd32d9ced9f47d276`;
- в таблице `users_user` появилась запись с флагом `is_active=True` (режим разработки, поведение управляется флагом `DEBUG`);
- сработала пост-сохраняющая сигнальная функция `create_user_profile`, автоматически создавшая связанный объект `Profile` с дефолтным инвентарём (`ai_summons=3`, `hint_scrolls=5`, `skeleton_scrolls=3`).

**Заключение по шагу:** ✅ пройден.

### 3.2. Шаг 2. Защита эндпоинта регистрации от автоматизированных атак

**Входные данные:** последовательность из 12 идентичных POST-запросов к `/api/auth/register/` с одного IP-адреса.

**Действия:** скрипт `curl -X POST` в цикле, имитирующий автоматизированную регистрацию (брутфорс/спам-фарм).

**Ожидаемый результат:** первые 5 запросов отрабатывают по бизнес-логике (создаются пользователи), последующие отклоняются с кодом `429 Too Many Requests` благодаря декоратору `@ratelimit(key="ip", rate="5/m", method="POST")`.

**Фактический результат:** соответствует ожидаемому. Сервер вернул `429` начиная с шестого запроса, ответ содержит человекочитаемое сообщение в поле `detail`.

**Заключение по шагу:** ✅ пройден.

### 3.3. Шаг 3. Аутентификация и получение JWT-токенов

**Входные данные:** учётные данные пользователя, созданного на шаге 1.

**Ожидаемый результат:** ответ сервера со связкой `{access, refresh}`, оба токена валидны в течение установленного времени жизни (`ACCESS_TOKEN_LIFETIME=60 мин`, `REFRESH_TOKEN_LIFETIME=1 день`); ротация refresh-токена при последующем обращении к `/api/auth/jwt/refresh/`.

**Фактический результат:** access-токен принят интерсептором axios на клиенте, успешно прикреплён в заголовок `Authorization: Bearer <token>` для последующих защищённых запросов. Ротация refresh-токена подтверждена опытно: после обращения к `/auth/jwt/refresh/` прежний refresh попадает в blacklist (`token_blacklist_blacklistedtoken`), что соответствует настройкам `ROTATE_REFRESH_TOKENS=True, BLACKLIST_AFTER_ROTATION=True`.

**Заключение по шагу:** ✅ пройден.

### 3.4. Шаг 4. Выбор игрового класса и инициализация прогрессии

**Действия:** пользователь переходит на страницу `/class`, выбирает класс «Маг Кода» (`ClassRole.id=1`).

**Ожидаемый результат:** на клиенте отправляется `PATCH /api/profile/me/` с телом `{"class_role": 1}`, на сервере обновляется связанная запись `Profile`, на интерфейсе появляется чип с названием класса и ранг «Новичок» (`Rank.slug="novice"`).

**Фактический результат:** профиль обновлён, на странице `/profile` отображены три ключевых элемента визуализации: имя пользователя, чип класса, чип ранга. Поле `Profile.current_rank` рассчитывается на лету как Python-property, что устраняет дублирование данных и риск рассинхронизации (см. фикс HIGH-01 в `docs/PRODUCTION_AUDIT.md`).

**Заключение по шагу:** ✅ пройден.

### 3.5. Шаг 5. Прохождение учебной миссии

**Действия:** пользователь открывает миссию идентификатором 1 (доступна без предварительных условий — `prerequisites=[]`), последовательно решает входящие в неё задачи трёх типов: чтение лекционного материала (story), выбор варианта в квизе (quiz), отправка кода в песочницу (code).

**Ожидаемый результат:** для каждой задачи создаётся объект `TaskProgress` со статусом `completed`; при завершении последней задачи вызывается `POST /api/missions/{id}/complete/`, который начисляет `mission.xp_reward` опыта, при пересечении порога уровня инкрементирует `Profile.level` и пополняет инвентарь.

**Фактический результат:**
- кодовая задача провалидирована песочницей: код `print(sum(range(1, 11)))` вернул `55` за 0.8 секунды, статус контейнера `exited (0)`;
- начисление XP отработало атомарно: `Profile.add_xp()` возвращает кортеж `(leveled_up, old_level, new_level)`, что позволяет фронту показать раздельные тосты «+10 XP» и «🎉 Уровень повышен!»;
- сигнал `post_save` на модели `Progress` создал/обновил запись в `LeaderboardEntry` для двух scope-ов: глобального и трекового, после чего пересчитал позицию пользователя;
- инвентарь пополнен на один свиток подсказки и один вызов AI за каждый набранный уровень (механика MID-07).

**Заключение по шагу:** ✅ пройден.

### 3.6. Шаг 6. Запуск пользовательского кода в защищённой песочнице

**Действия:** в редакторе кода миссии пользователь вводит пользовательский Python-код и нажимает кнопку «Run». Запрос уходит по WebSocket-каналу `/ws/runner/` для потокового вывода stdout/stderr.

**Ожидаемый результат:** код исполняется в одноразовом Docker-контейнере на образе `python:3.11-alpine`, без сетевого доступа (`network_mode="none"`), с ограничением памяти 128 MiB и числа процессов 64. По завершении выполнения контейнер уничтожается, журналы передаются клиенту фреймами по протоколу `multiplexed` Docker API.

**Фактический результат:** полностью соответствует ожидаемому. Дополнительно зафиксирована корректная отработка трёх угрожающих сценариев:

| Атака | Результат |
|---|---|
| Бесконечный цикл (`while True: pass`) | контейнер убит watchdog'ом по таймауту, ошибка возвращена клиенту с явным сообщением «Timeout: код выполнялся дольше 5 сек» |
| Попытка сетевого подключения (`socket.create_connection`) | исключение `OSError: Network is unreachable`, утечки данных не произошло |
| Попытка чтения файлов хоста (`/etc/shadow`, `/etc/passwd`) | возвращены файлы изолированной файловой системы контейнера, реальные хеши паролей хоста недоступны |

Перечисленные угрозы покрыты автоматизированными тестами в файле `backend/game/tests/test_sandbox_security.py` (см. раздел 4 настоящего отчёта).

**Заключение по шагу:** ✅ пройден.

### 3.7. Шаг 7. Защита от DDoS-нагрузки на дорогостоящие эндпоинты

**Действия:** скрипт выполнил 25 последовательных POST-запросов к `/api/runner/execute/` и 12 запросов к `/api/ai-assist/` от одного аутентифицированного пользователя.

**Ожидаемый результат (на основании настроек throttling):** для песочницы — 20 успешных запросов в минуту и максимум 5 запросов за 10 секунд (защита от спам-кликов кнопки Run); для AI-помощника — 10 запросов в минуту (квота сторонней Gemini API).

**Фактический результат:** для AI-помощника первые 10 запросов вернули `200 OK`, последующие два — `429 Too Many Requests` с локализованным сообщением; для песочницы наблюдение burst-лимита затруднено естественной задержкой Docker (~1 секунда на контейнер), однако прямой юнит-тест на throttle-классе подтверждает корректность ограничения (см. раздел 4).

**Заключение по шагу:** ✅ пройден.

### 3.8. Шаг 8. Обращение к AI-помощнику

**Действия:** пользователь нажимает кнопку «Призвать наставника» в контексте кодовой задачи, передавая текущий черновик кода и описание задачи.

**Ожидаемый результат:** запрос направляется в Gemini 1.5 Flash через официальный SDK `google-generativeai`, ответ модели — короткая (3–5 предложений) подсказка в RPG-стилистике, не раскрывающая полное решение. При успешном ответе из инвентаря пользователя списывается одно условное «обращение к AI» (`Profile.use_item("ai_summons")`). При исчерпании инвентаря возвращается `402 Payment Required` с пояснением.

**Фактический результат:** соответствует ожидаемому. Дополнительно проверено защитное поведение при недоступности модели: если `GEMINI_API_KEY` не задан, в ответе клиент получает локализованный fallback-текст («🔮 Мудрец молчит…»), при этом инвентарь не списывается (поведение реализовано через возврат кортежа `(text, success_flag)` из метода `_call_gemini`).

**Заключение по шагу:** ✅ пройден.

### 3.9. Шаг 9. Деавторизация и обнуление сессии

**Действия:** пользователь нажимает кнопку «Выйти», на клиенте удаляется пара JWT-токенов, на сервере вызывается `POST /api/auth/logout/`, который добавляет refresh-токен в blacklist.

**Ожидаемый результат:** после деавторизации защищённые маршруты возвращают `401 Unauthorized`, попытка повторно использовать сохранённый refresh-токен заканчивается ошибкой.

**Фактический результат:** соответствует ожидаемому.

**Заключение по шагу:** ✅ пройден.

## 4. Автоматизированная регрессия

Описанные в шаге 6 угрозы безопасности зафиксированы как автоматизированные тесты PyTest и встроены в состав CI-сборки (см. `.github/workflows/ci.yml`). Файл тестов: `backend/game/tests/test_sandbox_security.py`. Покрываемые сценарии:

| Идентификатор теста | Угроза | Метод проверки |
|---|---|---|
| `test_sandbox_kills_infinite_loop_by_timeout` | Истощение CPU хоста бесконечным циклом | Запуск `while True: pass`, ожидание принудительного завершения по таймауту watchdog'а |
| `test_sandbox_blocks_outbound_network` | Несанкционированная утечка данных во внешнюю сеть | Попытка установить TCP-соединение с `1.1.1.1:80`, ожидание исключения `OSError` |
| `test_sandbox_cannot_read_host_secrets` | Чтение чувствительных файлов хоста | Чтение `/etc/shadow`, `/etc/passwd`, `/proc/1/cgroup`; верификация отсутствия хешей паролей хоста |

Все три теста на момент составления отчёта проходят (`3 passed in 11.94s`). Регрессия запускается на каждый pull request в основную ветку.

## 5. Анализ выявленных дефектов

В ходе тестирования установлено, что текущая реализация удовлетворяет функциональным требованиям и базовым требованиям безопасности. Критических и высоких дефектов не выявлено. Обнаруженные в процессе настройки замечания (некорректная работа throttling из-за локального кэша, ошибка парсинга нестандартного интервала `5/10s` в DRF) устранены и задокументированы в журнале фиксов `docs/PRODUCTION_AUDIT.md`.

## 6. Заключение

Информационная система «RPG Academy» успешно прошла сквозное end-to-end тестирование по полному пользовательскому сценарию: регистрация → активация → аутентификация → выбор класса → прохождение миссии → исполнение кода в песочнице → обращение к AI-помощнику → деавторизация. Подтверждены: функциональная корректность, изоляция исполняемой среды, наличие защитных механизмов от спама и брутфорса, корректность атомарных операций начисления опыта и обновления ранга.

Система готова к демонстрации перед аттестационной комиссией и к использованию в учебном процессе на пилотной группе студентов.
