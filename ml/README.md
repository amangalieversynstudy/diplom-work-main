# Модель прогнозирования учебной результативности и риска ухода

Офлайн-конвейер: из данных получить таблицу «окно поведенческих признаков → исход курса / сводный балл результативности / уход»,
обучить классификационную и регрессионную модели, честно оценить их и выгрузить коэффициенты в компактный JSON,
который читает Django без numpy и scikit-learn.
Общий контракт признаков описан в `risk/schema.py`.

```
данные ──► таблица снимков ──► risk.train ──► model.json ──► RISK_MODEL_PATH ──► список EWS / прогноз результативности
 OULAD     (окно 28 дн.)        логистическая регрессия       (коэффициенты)       (причина «модель» и оценка 0–100)
 платформа (окно 14 дн.)        + градиентный бустинг
                                + Ridge-регрессия балла (0–100)
```

## Установка и проверка

```bash
pip install -r ml/requirements.txt
python -m pytest ml/tests
```

## 1. Метод на OULAD

OULAD (Open University Learning Analytics Dataset, Kuzilek, Hlosta, Zdrahal, 2017; лицензия
CC BY 4.0) скачивается отдельно, в репозиторий не входит. Положите распакованные csv в `ml/data/oulad/`
(нужны `studentInfo`, `studentRegistration`, `studentVle`, `studentAssessment`, `assessments`).

```bash
cd ml
python -m risk.train --oulad data/oulad --out out/oulad
```

Признаки берутся из первых 28 дней курса (`active_days`, `events`, `events_last_week`, `recent_share`,
`graded_attempted`, `graded_failed_share`), целевая переменная — итог курса (неуспешный исход Fail или Withdrawn = 1,
успешное завершение Pass или Distinction = 0; при передаче `include_performance=True` также прогнозируется
непрерывный балл результативности `performance_score` 0–100 через Ridge-регрессию).
Студенты, которые ушли раньше конца окна, исключаются: их исход уже известен. Тест — последний
семестр (`2014J`), обучение — предыдущие, порог подбирается на валидации, а не на тесте.
Результат: `out/oulad/report.md` (таблица метрик для главы диссертации), `report.json`, `model.json`.

`--window-days 14|21|28|42` показывает, как качество зависит от того, насколько рано делается прогноз.
Это и есть ответ на вопрос «через сколько дней прогноз становится полезным».

## 2. Рабочая модель на данных платформы

Модель, обученная на OULAD, **не подключается к платформе**: там она предсказывает итог курса OULAD, а
платформе нужен прогноз ухода в ближайшие две недели и оценка сводного балла результативности (0–100).
Бэкенд откажется загрузить файл с `source != "platform"`. Рабочая модель обучается тем же конвейером на данных пилота:

```bash
cd backend
python manage.py export_risk_features --include-performance --out ../risk_features.csv --performance-out ../performance.csv
cd ../ml
pip install -r requirements.txt          # обучать на своём компьютере: в образе Railway нет scikit-learn
python -m risk.train --features ../risk_features.csv --performance ../performance.csv --out ../risk_model
```

Выгрузка берёт только участников исследования (согласие и регистрация с `PILOT_STARTED_AT`), окна исхода
обрезает по `--until` (по умолчанию `PILOT_ENDED_AT`) и пишет в каждую строку уровень и балл правил из снимка
списка накануне (`rule_level`, `rule_score`). Если выгрузку запускать против боевой базы со своего компьютера,
нужен тот же `ANALYTICS_EXPORT_SALT`, что на сервере, иначе псевдонимы будут другими.

Затем на сервере задайте `RISK_MODEL_PATH=/путь/к/risk_model/model.json`. Файл перечитывается
при изменении, перезапуск не нужен. Если файл недоступен или испорчен, список раннего
предупреждения продолжает работать по правилам.

Выгрузка берёт моментальные снимки раз в `--step-days` после первых `--window-days` активности.
Метка `label` — 1, если ученик молчал следующие `--horizon-days`; при флаге `--include-performance`
добавляется столбец `performance_score` (сводный балл учебной результативности ученика по формуле 50/30/20).
В таблицу не попадают снимки с неизвестным исходом, снимки учеников без незаконченной миссии
(закончить курс — не значит уйти), окна без активности и всё, что идёт после первого ухода:
«молчал, и дальше молчит» тривиально и научило бы модель только тому, что неактивные неактивны.

## Как читать результат

- **Порог** выбран так, чтобы поймать не меньше 80% ушедших / неуспешных исходов. Цена — доля ложных тревог; её видно как
  `flagged_share` и `precision`.
- **Одиночный признак** в отчёте — планка, которую модель обязана превзойти. Если модель не лучше
  простого числа активных дней или кликов, на пилоте достаточно правил.
- **Коэффициенты** относятся к стандартизованным признакам. `active_days` и `events` сильно
  коррелируют, поэтому знак каждого по отдельности читать нельзя, только их совокупность.
- **Модель против простых планок на тех же строках** (`comparison` в report.json и раздел в report.md):
  ROC AUC модели, одного `active_days` и правил платформы (`rule_score`) на одних и тех же тестовых строках, разницы
  с 95% интервалом парного бутстрепа по ученикам. Правило решения записано до пилота: модель подключается, только
  если нижняя граница интервала разницы с лучшей планкой выше 0. Если в тесте меньше 10 уходов, отчёт прямо пишет,
  что числа не интерпретируются.
- **Прогноз сводного балла (`performance_regression`)**: с `--performance` — по одной строке на ученика (признаки
  первого окна, балл на конец периода), с планками «среднее обучающей части» и «регрессия только на `active_days`»,
  MAE, RMSE и R² с интервалами бутстрепа по ученикам. Без `--performance` регрессия считается по строкам выгрузки
  и помечена как не тот дизайн.
- Признаки намеренно только поведенческие: возраст, пол, регион и образование в модель не входят.
- Метрики на платформе имеют смысл только на выборке в сотни учеников с десятками уходов. На
  меньших данных обучение запустится, но отчёт будет шумом: смотрите на размеры `rows` в отчёте.
